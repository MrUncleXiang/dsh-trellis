# Feature PRD

## 背景

用户在用一套 Trellis 工作流插件（项目工作流触发器，包名 `@banana-peeljj12/dsh-trellis`），它原本只为 DSH（原运行宿主，一个 AI 运行环境）而写。现在用户日常改用 Codex（当前编程助手）干活，希望同一套工作流不要断：

- 原来在 DSH 里积累的任务数据、规范、技能、模板继续可用，不做格式迁移。
- 在 Codex 里也能创建任务、看当前任务、继续绑定任务、更新步骤、写产物、归档。
- 两个宿主共用同一份任务数据，不各存一套。
- 原作者仓库还在更新，用户要能持续把上游新版本合进来，不分家后各自演化。
- 用户自己的定制（项目专属技能、项目规范）不能在升级时被抹掉。

上一轮已在副本上验证与分析（证据见「相关代码/文档」）。结论：不能原样升级后就说双助手接通；本轮只做方案规划，不动业务实现。

## 范围

### In Scope

- 规划「上游原版 main（主分支）」与「用户维护分支」的关系，以及版本记录、升级、回退的做法。
- 规划两个宿主的接入入口（工具入口 + 会话自动提示），共用同一套任务操作逻辑与任务数据。
- 规划持续合并上游时的隔离规则：定制技能不被覆盖、旧模板不物理删除、继续只绑定、批准与普通更新隔离。
- 规划跨进程写入保护与会话标识校验的落点（不引入第二套 task.json）。
- 明确哪些能力尚未验收，哪些属于现有实现的字段级限制。

### Out of Scope

- 任何业务实现改动（不改 lib/、skills/、scripts/、package.json、安装配置）。
- 真实 DSH 进程与真实 Codex 工具注册、自动钩子的实际启用。
- 引入新的第三方依赖；MCP 相关依赖是否采用先列选项，等用户决定。
- 接入 DSH / Codex 以外的其他助手。
- 任务数据格式迁移、历史任务改写。

## 验收标准

- [ ] 规划文档给出 `main` 快进与维护分支合并的完整命令，以及不改共享分支历史的回退办法。
- [ ] 规划文档新增宿主无关的任务服务入口与文件系统、会话适配边界，并明确当前尚无公开任务核心 API。
- [ ] 规划文档说清两个宿主各自的入口，以及共用的任务逻辑与任务数据（不新增第二套 task.json）。
- [ ] 规划文档说清定制技能保护、旧模板不物理删除、继续仅绑定、全量 steps 更新同样验收、真实会话标识缺失拒绝。
- [ ] 规划文档说清跨进程锁的获取、释放、失效核对、多锁顺序与内容指纹比对。
- [ ] 规划文档说清真批准只来自宿主用户事件，并明确 `task.json` 仍为 `planning`、批准后转 `in_progress` 的状态转换；可信宿主批准事件列为实施前置条件（待验证），不可获取时由用户选择手动确认通道。
- [ ] 规划文档说清维护构建标识、受控 manifest 与 `.agents/skills/.trellis-version` 的准确路径，升级不只看上游 `version`。
- [ ] 明确当前 MCP 与自动钩子都待真实宿主验收，依赖选择待确认。
- [ ] 独立审查通过，结论记录在本任务 `design-review.md`（由主代理统一安排）。

## 约束与风险

- 本轮授权只到「规划 + 建分支 + 核对后推送」；双端接入的实现要等用户单独批准。
- 现有全量测试可能含物理删除清理逻辑，未审查前不运行。
- 上游仍在演进，维护分支越晚建立，后续合并冲突越大。
- 现有插件在版本变化时会把插件管理的全部技能与共享模板整份重写（见实测证据），定制内容有被覆盖风险。
